📅 2026-06-04

🏢 腾讯游戏中心
研究范围

本报告聚焦 LLM 推理全链路成本：从 Prefill/Decode 计算瓶颈到 KV Cache 经济性，从自部署 vs. API 成本结构到量化降本与开源模型部署差距，系统梳理推理成本的构成与优化路径。

五大核心结论

  • Prefill 是算力瓶颈，Decode 是带宽瓶颈 —— 同一模型两阶段的性能受限因素完全不同，优化策略需区分对待
  • KV Cache 缓存价值远超输出缓存 —— 前缀匹配宽松（命中率 90%+），输出缓存命中率 <1%，工程上不可用
  • 自部署成本高 3~10x 的主因是运维人力 —— 硬件摊销仅占 28%，运维人力占 68%，盈亏平衡需 >416M tokens/月
  • INT8 量化是推理性价比最优选 —— 显存减半、精度损失 <0.5%，AWQ 速度快、GPTQ 精度高
  • 开源部署性能约为原厂 70~90% —— 差距来自未开源的 MoE 专用 Kernel，随时间逐渐缩小

1. Prefill 与 Decode 计算瓶颈分析

核心结论

Prefill 可并行，是算力瓶颈（Compute-Bound）；Decode 必须串行，是显存带宽瓶颈（Memory-Bound）。两者开销差异的根源是并行性，不是参数量。

LLM 推理分两个阶段。Prefill 将用户输入的所有 token 并行通过模型，生成 KV Cache；Decode 基于 KV Cache 逐 token 自回归生成输出。同一个模型权重，在数据形态和计算模式上有本质差异。

✅ Prefill（预填充）

  • 输入 N 个 token 已知且完整
  • 矩阵×矩阵乘法（GEMM），GPU 利用率 >80%
  • KV Cache 只写一次，N 个 token 共享
  • 瓶颈：算力（TTFT 随输入长度线性增长）
  • 优化：Flash Attention（分块计算，显存 O(N)）

⚠️ Decode（逐 token 生成）

  • 每步只有 1 个 token，依赖上一步输出
  • 矩阵×向量乘法（GEMV），GPU 利用率 <20%
  • 每 token 都要重读全部权重从 HBM
  • 瓶颈：显存带宽（HBM 吞吐决定 TPS）
  • 优化：Speculative Decoding、MoE

开销维度定量对比

以 70B 模型、输入 2K token、输出 500 token 为例：

维度PrefillDecode
总计算量（FLOPs）~280T（2K × 140B）~70T（500 × 140B）
显存权重读取次数1 次（N 个 token 共享）500 次（每 token 重读）
总权重搬运量~140GB（读 1 次）~70TB（500 × 140GB）
GPU 利用率高（~80%）低（~15%）
瓶颈类型算力（Compute-Bound）显存带宽（Memory-Bound）
用户感知指标TTFT（首 token 延迟）TPS（每秒生成 token 数）

MoE 模型的特殊情况

Prefill 阶段当输入足够长时，N 个 token 路由到的 Expert 集合（Union）可能覆盖几乎所有 Expert，此时从 HBM 读取的有效参数量接近全量。但即便如此，Prefill 的并行性仍使其比 Decode 快得多。

2. KV Cache 与 Prompt Caching 机制

核心结论

KV Cache 缓存的是"计算过程"（可复用、命中率高）；输出缓存的是"计算结果"（相同输入未必有相同输出，命中率极低）。

LLM 推理的 Prompt Caching 机制，缓存的是输入 token 在模型各层的 Key/Value 向量（即 KV Cache），而非最终输出 token。其经济学逻辑是：KV Cache 的命中率远高于输出缓存，且单位存储的复用价值更高。

KV Cache 缓存 vs. 输出缓存：多维度对比

维度KV Cache 缓存输出缓存
缓存对象中间计算结果（KV 向量）最终输出 token 序列
命中条件输入前缀相同（宽松）输入完全相同 + temperature=0（极严）
命中率高（system prompt 固定可达 90%+）极低（<1%，输入稍变即失效）
命中后收益省掉前缀 Prefill 计算（约 90% 折扣）直接返回缓存（100% 省）
存储开销中等（seq_len × hidden_dim × 2 × layers）极大（每 token 需存完整 logits）
工程实用性✅ 主流推理引擎均支持❌ 学术探索，工程不可用

计费逻辑分析

以 Anthropic Claude 为例，命中缓存的 Input Token 按 $0.30/MTok 计费（原价 $3/MTok，相当于 10% 价格）；Output Token 价格不变。前提是相同前缀的 Prompt 在 5 分钟内再次请求，缓存才生效。

// Prompt Caching 命中判定（伪代码）
function isCacheHit(currentPrompt, cachedPrefix):
  cachedTokens = 0
  for i, token in enumerate(currentPrompt):
    if token == cachedPrefix[i]:
      cachedTokens += 1
    else:
      break
  return cachedTokens >= 1024 // 至少 1024 token 匹配才命中

// 命中后计费
cost = cachedTokens × $0.30/1M + (totalTokens - cachedTokens) × $3.00/1M

3. 自部署 vs. API 采购成本结构

核心结论

自部署成本高 3~10x 的主因不是"硬件贵"，而是 GPU 利用率低（20~40% vs. 60~80%）、隐性运维成本，以及规模效应差距（API 厂商多租户分摊硬件成本）。

以 70B 模型为例，自部署需要约 8 × A100 80G（约 $120K 硬件投入，3 年摊销约 $3.3K~$5.5K/月）。加上电费、运维人力（0.5~1 人），月固定成本约 $10K~$15K。API 采购按 token 付费，无前期投入。

关键洞察

自部署的隐性成本中，运维人力占比最高（68%）。相比之下，API 采购是纯变量成本，适合调用量波动大的场景。当每月调用量 > 416M tokens 时，自部署才开始具备经济优势。

此外，vLLM / TensorRT-LLM 等开源推理引擎可将 GPU 利用率提升至 50~60%，能把盈亏平衡点向左推约 20~30%。

4. LLM 量化原理与工程实践

核心结论

量化 = 把 FP16 权重用 INT8/INT4 整数表示。核心公式是找 scale + zero_point 把浮点范围映射到整数域。PTQ 速度快，QAT 精度高；工具选 AWQ（速度快）或 GPTQ（精度高）。

量化的理论基础是 LLM 权重分布集中（大部分权重在 0 附近），用低精度整数近似表示，精度损失小、显存收益大。

核心公式：非对称量化

// INT8 非对称量化公式
  scale     = (FP16_max − FP16_min) / 255
  zero_point = round(−FP16_min / scale)
  INT8_val   = clip(round(FP16_val / scale) + zero_point, 0, 255)

// 反量化（推理时用）
  FP16_val ≈ (INT8_val − zero_point) × scale

常见量化精度对比

精度每权重字节70B 模型大小精度损失适用场景
FP162 bytes140 GB无训练 / 高精度推理
INT81 byte70 GB极小 (~0.1–0.5%)推理（推荐）
INT40.5 byte35 GB小 (~1–3%)显存极度受限
INT30.375 byte~26 GB明显 (~3–8%)实验性

PTQ 训练后量化步骤

① 用校准数据集跑 FP16 模型，记录每层激活值分布；② 计算 scale + zero_point；③ 量化权重并保存。全过程不需要重新训练，几分钟到几小时即可完成。

GPTQ vs. AWQ 工具对比

GPTQ（精度优先）

  • 用 Hessian 矩阵近似决定量化顺序
  • 量化某权重时，补偿对其他权重的量化误差
  • INT4 精度损失极小（接近 INT8 PTQ）
  • 缺点：量化速度慢（需计算 Hessian）

AWQ（速度优先）

  • 观察激活值分布，找"重要通道"
  • 重要通道的保护更精细（INT8 或保留 FP16）
  • INT4 精度损失小，量化速度快
  • 缺点：需校准数据集跑一遍激活值

5. 开源模型部署差距与优化路径

核心结论

原厂（如 DeepSeek）跑自家模型，用了大量未完全开源的定制 CUDA Kernel 和通信优化。第三方用 vLLM 部署，性能通常只有官方 API 的 70–90%，差距主要来自未开源的 MoE 专用优化。

以 DeepSeek-V3 为例：原厂开源了模型权重和架构代码，但 MoE 专用 Flash Attention 变体、FP8 推理 Kernel、多机 All-to-All 通信优化等深度定制部分未完全开源。开源社区（vLLM）需要时间跟进，存在时间差。

原厂优化 vs. 开源框架

DeepSeek-V3 部署为例：

优化项原厂官方 API开源框架（vLLM）差距
MoE Expert 调度定制融合 KernelPython 层调度 + 通用 Kernel通信开销更大
FP8 推理定制反量化 Kernel依赖 vLLM 通用 FP8 支持约 5–10% 速度差

部署效率提升建议

立竿见影（优先级高）

  • 使用 vLLM + Flash Attention 2/3
  • 启用 PagedAttention（KV Cache 管理）
  • INT8 量化（GPTQ 或 AWQ）
  • Grouped-Query Attention（减少 KV 头数）

进阶优化（需定制）

  • MoE 模型的 Expert 并行策略调优
  • FP8 量化（需 Hopper 架构，H100+）
  • 定制 CUDA Kernel（需 CUDA 编程经验）
  • 多机部署时的通信策略优化

趋势判断

随着时间推移，开源社区对主流开源模型（Llama 3、DeepSeek-V3、Qwen 2.5）的优化会逐渐完善，原厂 vs. 第三方部署的性能差距会从 30% 缩小到 5–10%。但原厂永远拥有先发优势——最新优化在自己 API 上先跑。
